# 선수 사진을 사용자가 채운다 — 설계

작성 2026-09-28. 팬카드 사진 저장소를 비공개로 돌리는 일을 함께 다룬다.

## 왜

지금은 `collect-player-photos` 가 K리그 CDN 에서 선수 프로필 사진을 받아 줄인 뒤 공개 버킷
`player-photos` 에 올리고, 앱이 그 공개 주소를 그린다. 남의 사진을 **우리가 복제해 재배포**하는
구조다. 선수의 초상권·퍼블리시티권(부정경쟁방지법 2조 1호 타목)과 앱스토어 심사 지침 5.2.1 에도
걸린다.

알아본 대안은 모두 막혔다.

- 핫링크: 원본이 장당 약 3.1MB(1500×2000 PNG)라 스쿼드 한 번에 100MB 를 넘고, 초상권·5.2.1 은
  그대로다
- 공식 API: K리그 Open API 는 키 발급이 "준비 중"이고 사진 필드가 없다. BEPRO 는 B2B 계약형이고
  역시 사진이 없다
- AI 로 다시 그리기: 알아볼 수 있으면 퍼블리시티권은 그대로다

그래서 앱은 선수 사진을 제공하지 않는다. 사용자가 자기 앨범에서 골라 채우고, 채운 사진은 본인만
본다.

팬카드도 같은 문제를 안고 있다. 표는 본인만 읽지만 사진은 공개 버킷 `fan-cards` 에 있어, 주소를
아는 사람은 로그인 없이 연다. 얼굴 사진이 들어가는 물건이다.

## 잘 됐다고 보는 기준

- 우리 서버가 선수 사진을 공개 주소로 내보내는 곳이 0 이다
- 팬카드 사진은 로그인한 본인만 연다
- 사진이 없어도 카드와 프로필이 완성된 모습이다
- 코드에서 `getPublicUrl` / `object/public` 이 아바타 말고는 남지 않는다

## 정한 것

| 질문                                 | 결정                                                   |
| ------------------------------------ | ------------------------------------------------------ |
| 사용자 사진을 어디에 보여 주나       | 선수 프로필과 홀로 카드. 스쿼드 목록은 전원 실루엣     |
| 비로그인 사용자가 사진 넣기를 누르면 | 로그인부터 청한다 (신고·차단과 같은 흐름)              |
| 누끼                                 | 카드 만들기와 같이 자동으로 따고 원본/누끼 전환을 둔다 |
| 이미 모은 선수 사진 35장과 수집기    | 새 빌드 설치 뒤 버킷·함수·크론을 모두 지운다           |
| 저장 방식                            | 스토리지만 쓴다. 표를 두지 않는다                      |

**하지 않는 것**: 사진 공유, 남의 카드 보기, 공개 랭킹, "K리그 사진 불러오기" 같은 자동 채우기.
앱이 사진을 대신 가져오는 순간 우리가 복제 도구를 내미는 셈이 된다. 사용자가 자기 앨범에서
고르는 것까지만 한다.

**범위 밖**: 소식 썸네일(`news-thumbs`), 아바타 버킷(댓글에서 남에게 보이라고 만든 것이라
공개가 맞다), 연맹·구단에 보낼 허락 메일.

## 화면 흐름

### 선수 프로필 (`PlayerScreen`)

- 사진 틀에 내가 넣은 사진이 있으면 그것을, 없으면 `PlayerSilhouette` 를 그린다
- 틀을 누르면 지금처럼 카드 오버레이가 열린다
- 틀 모서리에 작은 카메라 배지를 달아 무엇을 넣을 수 있다는 것을 알린다

### 카드 오버레이 (`PlayerCardOverlay`)

사진 편집은 여기서만 한다. 결과를 카드 위에서 바로 본다.

- 사진이 없을 때: `[사진 넣기]`
- 사진이 있을 때: `[바꾸기]` `[치우기]`
- 방금 골랐고 누끼가 됐을 때만: `[원본/누끼]` 전환 추가
- 비로그인 상태에서 누르면 로그인을 청한다

### 사진 넣기

1. `ImagePicker` 로 고른다. 3:4 로 자른다 (카드의 사진 자리 비율)
2. 기기에서 누끼를 딴다 (`removeBackground`, `trim: true`). 실패하면 원본을 쓴다
3. 로컬 파일로 카드에 곧바로 그린다. 올라가기를 기다리지 않는다
4. 뒤에서 폭 1000 으로 줄여 올린다 (`expo-image-manipulator`). 누끼는 투명도를 지키려고 PNG,
   원본은 JPEG. 1000 은 기존 수집기가 홀로 카드용으로 실측한 폭이다
5. 전환을 누르면 다른 쪽 파일로 다시 올린다. 서버에는 늘 한 장만 있다. 전환은 방금 고른 동안에만
   된다 — 앱을 다시 켜면 서버의 한 장만 남는다 (팬카드와 같은 제약)
6. 올리기가 실패하면 알리고 카드를 이전 상태로 되돌린다

누끼·고르기 로직은 `CardMakerScreen` 에 있는 것을 훅(`usePickedPhoto`)으로 빼서 두 화면이 함께
쓴다.

### 치우기

확인을 받고 파일을 지운다. 실루엣으로 돌아간다.

## 데이터 흐름

### 저장소

- 비공개 버킷 `my-player-photos`. 5MB 상한, `image/png`·`image/jpeg` 만 받는다
- 경로 `{uid}/{playerId}` — **확장자 없이 고정**한다. 원본(JPEG)과 누끼(PNG)를 오가도 같은
  자리를 덮어써 옛 파일이 남지 않는다. 형식은 contentType 이 든다
- 시즌을 넣지 않는다. K리그 선수 ID 는 시즌이 바뀌어도 같고, 사진은 선수에 붙는다
- 정책: select / insert / update / delete 모두 `(storage.foldername(name))[1] = auth.uid()::text`
  (0009 의 팬카드 정책과 같은 모양)

### 내가 넣은 선수 목록

- 내 폴더를 한 번 나열한다 (`storage.from('my-player-photos').list(uid)`)
- 결과는 `playerId → updated_at` 만 담는다
- 질의 열쇠 `['myPlayerPhotos', uid]` — 누구의 답인지 열쇠에 넣는다 (`adminKey` 와 같은 이유).
  주소가 안 들어 있으므로 기기에 저장되어도 만료될 것이 없다

### 그리기 — 서명 주소를 화면에 흘리지 않는다

질의 캐시가 기기에 저장되고(`PersistQueryClientProvider`) expo-image 디스크 캐시는 주소를 열쇠로
쓴다. 서명 주소를 그대로 흘리면 만료된 주소가 재시작 뒤에도 살아남고, 발급할 때마다 캐시가
빗나간다.

그래서 해석기가 **기기 캐시의 파일 경로**를 돌려준다.

- `usePlayerPhoto(playerId): string | null`
- 캐시 자리: `cache/player-photos/{uid}/{playerId}@{updated_at}`
- 파일이 있으면 그대로 쓴다. 네트워크를 안 탄다
- 없으면 그때만 서명 주소(60초)를 받아 내려받아 둔다
- 같은 선수의 다른 버전 파일은 지운다
- Skia `useImage` 도 로컬 파일을 읽으므로 카드를 열 때마다 다시 받지 않는다

해석기는 버킷·경로·버전을 받는 일반 부품(`privateImage`)으로 두고, 선수 사진과 팬카드가 함께
쓴다.

### 올리기·치우기·로그아웃

- 올리기가 성공하면 방금 고른 파일을 그 버전 이름으로 캐시에 옮기고 목록을 무효화한다. 방금 올린
  것을 다시 받지 않는다
- 치우기는 파일을 지우고 목록을 무효화한다
- 로그아웃하면 `cache/player-photos/{uid}` 를 비운다

### 팬카드

- `fan_cards.photo_url` → `photo_path` 로 바꾼다. migration 이 기존 공개 주소에서
  `{uid}/{cardId}.jpg` 만 잘라 낸다
- 버킷 `fan-cards` 를 `public = false` 로, "fan-cards public read" 정책을 본인 읽기로 바꾼다
- 화면은 같은 해석기를 거친다. 버전은 `fan_cards.updated_at`
- `isUploadedPhoto` 는 "주소 모양" 대신 "경로인지 로컬 파일인지" 로 가른다
- 확인할 것: `uploadCardPhoto` 가 누끼 PNG 를 `image/jpeg` 로 올리고 있을 수 있다. 실제 바이트를
  보고 맞으면 함께 고친다

## 오류 처리

| 상황                | 처리                                                     |
| ------------------- | -------------------------------------------------------- |
| 목록 나열 실패      | 실루엣. 화면에 다시 들어올 때 재시도. 카드는 막지 않는다 |
| 내려받기 실패       | 실루엣. 알리지 않는다. 다음에 열 때 재시도               |
| 누끼 실패           | 원본을 쓴다                                              |
| 사진 접근 거부      | "설정에서 켜 주세요" 알림 (기존 문구 형식)               |
| 올리기 실패         | 알리고 카드를 이전 상태로 되돌린다                       |
| 올리는 중 세션 만료 | 로그인을 청한다                                          |
| 5MB 초과            | 폭 1000 으로 줄여 사실상 없다. 나오면 올리기 실패와 같게 |

## 테스트

### 자동 (jest)

- 경로·캐시 파일 이름 만들기
- 목록 응답을 `playerId → 버전` 으로 바꾸기
- 해석기 (supabase·파일시스템 가짜)
  - 캐시에 있으면 네트워크를 부르지 않는다
  - 없으면 서명받아 내려받는다
  - 버전이 바뀌면 새로 받고 옛 파일을 지운다
- 팬카드: 옛 공개 주소가 든 행도 경로로 읽는다 (migration 이 놓친 행에 버티기)
- 올리기 실패 시 되돌리기

### 배포 뒤 실측

- migration 직후
  - `fan_cards.photo_path` 에 `http` 로 시작하는 행이 0
  - 기존 팬카드 사진의 옛 공개 주소가 더는 안 열린다 (400/404)
  - 로그인 없이 `my-player-photos` 를 읽으면 막힌다
- 폰에서: 사진 넣기 → 누끼 전환 → 앱 재시작 뒤에도 남는지 → 치우기 → 로그아웃 후 다른 계정에서
  안 보이는지
- 정리 뒤: `player-photos` 공개 주소가 404. 코드에 `getPublicUrl` / `object/public` 이 아바타
  말고 없다

## 순서

1. migration: `my-player-photos` 버킷과 정책, `fan-cards` 비공개 전환, `photo_url` → `photo_path`
2. 앱 코드 (해석기, 선수 사진 흐름, 팬카드 전환, 스쿼드 목록 실루엣, 공개 주소 쓰던 곳 제거)
3. 새 빌드를 폰에 설치하고 실측
4. 정리: `player-photos` 버킷 객체와 버킷, `collect-player-photos` 함수, 앱·서버의
   `playerPhotoUrl` 과 `photo-client.ts`. 크론 등록은 migration 에 없다 — 지우기 전에
   `cron.job` 을 조회해 남은 잡이 있는지 본다

옛 빌드는 본인 폰에만 있으므로 1 과 3 사이에 잠깐 깨져도 영향받는 사람이 없다.

migration 을 API 로 돌리지 못한다(`database/query` 403). 1 은 SQL Editor 에 붙여 넣어 돌린다.
